## 0. 回退策略（本计划的核心约定）

**整站物理快照 + 整库快照，回退时一起还原到同一时刻。**

- **代码回退**：部署前 `tar` 整个 `/var/www/seat`（含 SeAT 核心、所有插件 `vendor/`、发布的静态资源、`.env`）。回退 = 解压覆盖。
  - 不靠 `composer require 旧 commit`：本分支是 **dev 分支**，commit 可能被 `--force-push` 覆盖而消失，物理快照不受影响。
- **数据库回退**：部署前 `mysqldump` 整库。回退 = 导入还原。
  - **不使用 `migrate:rollback`**：本次迁移的 `down()` 有损（精度收窄、删列丢消费标记，见 §6）。
- **一致性**：备份与恢复都在**维护模式 + 队列暂停**下进行，保证代码与数据库是同一快照点，回退损失趋近于零。

> **已确认（2026-06-06 只读巡检 prod）**：生产当前为 `1.0.0`（`98eab22`，巡检时 composer 显示为 `dev-dev-shop`，现已整理为 tag `1.0.0` / 分支 `shop`），确属旧版本，本次为**跨版本切换**，会触发抽奖 / 银行化迁移（§1.2）。
> 因此走「§3 全量备份 → §4 部署（含迁移）→ §5 验证」，回退靠 §7 物理快照还原。
> 回退目标版本（参考）：tag `1.0.0`（`98eab22`）；但实际回退以 §3 物理快照为准，tag 仅作锚点。

## 3. 备份（部署前必做 · 改动类 · 先确认）

> 这是整个回退方案的安全底座。务必在**维护模式 + 队列暂停**下做，保证快照一致。

### 3.1 进入维护模式 + 暂停队列

```bash
cd /var/www/seat
sudo -u www-data php artisan down --render="errors::503"

# 暂停队列 worker（prod 用 supervisor）
sudo supervisorctl status               # 先看管了哪些 program
sudo supervisorctl stop all             # 停全部 worker（如混管非 SeAT 进程，改成只停 SeAT 对应 program）
```

### 3.2 整库备份

```bash
TS=$(date +%Y%m%d_%H%M%S)
BACKUP_DIR=/var/backups/seat
sudo mkdir -p "$BACKUP_DIR"

# DB 凭据读 /var/www/seat/.env 的 DB_DATABASE / DB_USERNAME / DB_PASSWORD
sudo mysqldump --single-transaction --quick --routines --triggers \
  -u <DB_USER> -p'<DB_PASS>' <DB_NAME> \
  | sudo tee "$BACKUP_DIR/seat_db_${TS}.sql" > /dev/null

sudo ls -lh "$BACKUP_DIR/seat_db_${TS}.sql"     # 确认非空
```

### 3.3 整站代码备份（tar）

```bash
# 保留属主/权限（-p），归档内路径为 seat/...，便于原地还原
sudo tar -czpf "$BACKUP_DIR/seat_code_${TS}.tar.gz" -C /var/www seat

sudo ls -lh "$BACKUP_DIR/seat_code_${TS}.tar.gz"   # 确认非空
```

> 该归档含 `vendor/`（核心 + 所有插件）、`public/web/` 静态资源、`.env`、`storage/`。回退时解压即整体还原，**不依赖远程 git commit 是否还在**。

### 3.4 记下本次 TS

把 `${TS}` 值记录到部署记录，§7 回退要按它定位两个备份文件。

## 6. 为什么不用 `migrate:rollback`（迁移 down() 风险表）

回退靠 §7 物理快照，**不走 rollback**。下表是依据：

| 迁移 | down() 行为 | 风险 |
|------|-------------|------|
| `widen_pap_value_precision` | `value` 收窄回 decimal(5,2)/(6,2) | ⚠️ **高**：累计消费超 ±999.99 会截断/报错 |
| `add_bank_ledger_columns` | 删 `is_consumption`/`consumption_key`/`source`/`external_ref`/`ref_group` | ⚠️ **高**：丢消费标记，三口径口径回退 |
| `create_pap_audit_tables` | drop `pap_adjustments` + 删 paps 两列 | ⚠️ 高：丢全部审查/调整记录 |
| `extend_calendar_tags_analytics_enum` | `lottery` 行改回 `untracked` 再收窄 enum | ⚠️ 中：丢抽奖 tag 语义 |
| `create_lottery_tables` | drop 三张抽奖表 | ⚠️ 中：删抽奖历史 |
| `cleanup_deprecated_notification_settings` | 空操作 | 低：不可逆但无害 |

## 7. 回退方案（物理快照还原）

> 触发条件：§5 验证不通过，或上线后发现数据/功能异常且无法快速修复。
> 原则：代码与数据库**一起**还原到 §3 的同一快照点。

```bash
cd /var/www/seat
TS=<部署时记录的快照时间戳>
BACKUP_DIR=/var/backups/seat

# 7.1 维护模式 + 停队列
sudo -u www-data php artisan down
sudo supervisorctl stop all

# 7.2 还原代码：先挪走当前目录，再解压快照
sudo mv /var/www/seat /var/www/seat_broken_${TS}
sudo tar -xzpf "$BACKUP_DIR/seat_code_${TS}.tar.gz" -C /var/www
#   解压后 /var/www/seat 即回到备份时状态（含 vendor / .env / public）

# 7.3 还原数据库（覆盖现有数据，确认库名正确）
sudo mysql -u <DB_USER> -p'<DB_PASS>' <DB_NAME> < "$BACKUP_DIR/seat_db_${TS}.sql"

# 7.4 清缓存 + 恢复服务
cd /var/www/seat
sudo -u www-data php artisan config:clear
sudo -u www-data php artisan route:clear
sudo -u www-data php artisan cache:clear
sudo -u www-data php artisan view:clear
sudo supervisorctl start all
sudo -u www-data php artisan up

# 7.5 确认回退成功后，再清理 seat_broken_${TS}
```

> 因为代码与数据库同源同时刻，还原后版本一致，无需任何 composer / migrate 操作。
> 整库还原会把库回到备份点——这正是部署期开维护模式 + 停队列的意义：备份点之后几乎无新写入，回退损失趋近于零。
