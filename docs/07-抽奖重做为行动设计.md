# 07 · 抽奖重做为「行动」设计

> **本文档推翻 [`05`](05-抽奖外移与PAP银行化设计.md) 的几条核心决策。** 05 把抽奖降级成"月度消费锚 + 实时扣 + 外部消费审查页";本方案把抽奖**恢复成「行动」**:一场抽奖 = 一个 operation,开奖人 = 负责人,进**现成的行动审查页**。
>
> **状态(2026-06-03):设计已定稿,待实现。** 决策来源:与组织者的设计对话,6 项已逐条拍板(见 §3)。

---

## 1. 背景:为什么推翻 05 的"消费锚"方案

05 为了"SeAT 纯银行 + 实时扣",把抽奖建模成和商店一样的**月度消费锚**(`standingFor`),并为它新建了一个**外部消费审查页**。实际评审中发现这套有三个不顺:

1. **抽奖天然是"行动"**:它有开奖人(可作负责人)、有"一场"的概念、应该能审查。降成"月度账本锚"丢掉了这些属性。
2. **凭空多一个页面**:抽奖被踢出行动审查页后,只好新建"外部消费审查页"来装它——这个页面纯粹是"抽奖被降级"的补偿品。
3. **实时扣其实没必要**:05 坚持"每买一个节点实时扣"是为了防双花。但抽奖由军团组织、**同一时间只有一场**(未来个人抽奖也可约束"有未开奖场次就不许参加新场"),根本不存在并发赊账 → 实时扣的前提不成立。

**结论**:抽奖**开奖后**把整场作为**一个行动一次性结算**,既解决"每节点一行动太多",又让"开奖人当负责人"时序成立(开奖时负责人已存在)。

> 05 §7.3 曾否决"每场抽奖注册成一个 operation",理由是"救不回玩法审查"。但本方案**不要玩法审查**(节点/中奖留外部),只要"资金归场次 + 负责人 + 进行动审查"——那条否决理由不适用。

---

## 2. 核心模型:两个标记表达三类 operation

新模型有三类 operation,**复用 bank 已加好的 `is_consumption` + `analytics=lottery` 两个标记**即可区分,**不需要加新列**:

| 类型 | `is_consumption` | 挂 `lottery` tag | 算消费? | 进行动审查页? |
|---|---|---|---|---|
| 出勤行动 | 0 | 否 | 否(出勤) | ✅ |
| **抽奖** | 1 | **是** | 是 | ✅ |
| 商店扣款锚 | 1 | 否 | 是 | ❌ |

- **消费口径**(出勤 − 消费 = 可用):照旧按 `is_consumption` 判定,抽奖和商店都算消费,**恒等式不变**。
- **行动审查页过滤**:从 `WHERE is_consumption = 0` 改为 **`WHERE is_consumption = 0 OR analytics = 'lottery'`** —— 出勤 + 抽奖显示,商店锚(无 lottery tag)排除。
- 抽奖 operation 挂 `analytics=lottery`、`quantifier=0` 的保留 tag(沿用内置抽奖的 `Lottery::reservedTag()` 思路):基础 PAP = 0,参与者最终值 = 0 + 负调整 = 负值(消费)。

## 3. 已拍板的 6 项决策

| # | 决策 | 选择 |
|---|---|---|
| 1 | 抽奖如何提交扣款 | **新增「开奖结算」接口**,开奖后一次性提交整场 |
| 2 | 实时 debit/refund | **保留**给未来商店;抽奖不再用 |
| 3 | 抽奖纠错 | **走行动审查的奖惩调整**(抽奖已是 operation,现成机制) |
| 4 | 外部消费审查页 | **砍掉** |
| 5 | 结算时余额不足 | **扣成负值、如实记账**(钱已在外部押出,负值由 FC 事后审查纠正,不阻断结算) |
| 6 | 商店预留代码 | **挑到"商店预留"区 + 注明"当前无调用者"** |

## 4. 抽奖新流程与接口

```
玩家点抽奖 → JWT 跳外部(保留) → 外部跑购买/抽奖(不扣款,赊账期)
   → 开奖 → 外部调【开奖结算接口】一次性提交整场
      → SeAT 建一个 operation(负责人=开奖人,挂 lottery tag,is_consumption=1)
         → 给每个参与者写负值 PapAdjustment + recompute(余额不足扣成负)
            → 该 operation 进行动审查页;纠错走审查奖惩调整
```

### 4.1 新增「开奖结算」接口(写 token)

```
POST /api/calendar/lottery/settle
{
  "ref_group": "lottery:3",                  // 场次标识
  "settled_by_character_id": 2118151113,     // 开奖人 → operation 负责人(user_id + fc_character_id)
  "title": "第3期超网抽奖",
  "idempotency_key": "lottery-3-settle",     // 整场一个,幂等:重复提交返回已建 operation
  "participants": [
    { "character_id": 2118…, "amount": 10.00, "reason": "押注节点 #03, #07" },
    { "character_id": 2118…, "amount": 5.00,  "reason": "押注节点 #11" }
  ]
}
```

**服务端逻辑(单事务 + 幂等)**:
1. **幂等**:`idempotency_key` 命中 → 直接返回上次建的 operation(不重复结算)。
2. 解析 `settled_by_character_id` → SeAT user + 主角色 → 作 operation 的 `user_id` / `fc_character_id`(满足外键)。
3. 建 operation:`title`、`is_consumption=1`、挂 lottery 保留 tag、`start_at/end_at=now`。
4. 逐个 participant:`character_id` 聚合到主角色 → `Pap::firstOrCreate` + 负值 `PapAdjustment`(`source=lottery`、`ref_group`、`reason`)→ `recomputeValueFor`。**余额不足照扣成负**(决策 5)。
5. 返回:`operation_id` + 各参与者 `balance_after`。

> 幂等键落点:给 operation 加一个唯一列(如 `settle_key`),或复用 `consumption_key` 的唯一约束承载 `idempotency_key`。实现阶段定。

### 4.2 退款 / 提前开奖 / 取消

- **开奖前取消**:因为"开奖后才扣",取消时**根本没扣过款**,SeAT 不涉及,外部自理。
- **提前开奖**:未售节点外部作废,只把**已售**的参与者放进 `settle` 的 `participants`。
- **结算后纠错**:走行动审查的奖惩调整(决策 3),不需要抽奖专用 refund。

## 5. 改动清单

**加**
- `POST /api/calendar/lottery/settle` 接口 + 控制器(建 operation + 挂 lottery tag + 批量负值扣款 + 幂等)。

**改**
- 行动审查列表过滤:`is_consumption=0` → `is_consumption=0 OR analytics='lottery'`(让抽奖 operation 回到审查页)。

**砍**
- 外部消费审查页整套:路由 `calendar/audit/consumption*`、`AuditController::consumptionIndex/Json/DetailJson`、`views/audit/consumption*`。

**保留(抽奖不再用,挪入「商店预留」区 + 注释,决策 2/6)**
- 实时 `debit`/`refund` 接口、`ApiWriteTokenMiddleware`、`Operation::standingFor()`(月度消费锚)、`is_consumption` 列。
- > `standingFor` 的 `user_id=0` 外键 bug 已在 `ea5b6fb` 修复(改用调用者 `$user->id`);该修复对"商店将来用 debit"仍然必要,保留。

**保留不动**
- 抽奖外链跳转 `lottery.redirect` + JWT、余额查询 API、lottery 三表(归档)。

**历史数据天然兼容**
- 内置时代的抽奖 operation 本就 `is_consumption=1` + 挂 lottery tag → 新过滤下**自动出现在行动审查页**,无需迁移。

## 6. 统计口径核对(必须保持)

- 消费判定仍是 `is_consumption`,抽奖 operation `is_consumption=1` → 仍算消费 → **"出勤 − 消费 = SUM(value) = 可用"恒等式不变**。
- 抽奖参与者的 `paps.value` 仍是负值,口径同旧;主角色聚合不变。
- 改完后逐页核对恒等式 + 主角色聚合 totals 不放大/丢失(验证清单沿用 03 / 06 §9)。

---

## 7. 待实现 / 风险

- **结算接口的并发与幂等**:整场一个 `idempotency_key` + 唯一约束 + 事务,防重复结算;批量写多个参与者要在一个事务里。
- **余额不足扣成负**(决策 5):`total_pap` 对外仍 `max(0,…)` 兜底不显负;负值由 FC 在行动审查里纠正。
- **赊账窗口边界**:当前安全(同时只有一场抽奖、商店已下线)。**若将来商店恢复且实时扣**,"抽奖赊账 + 商店实时扣"之间理论可双花——届时需把商店也纳入约束或单独处理(记此一笔)。
- **外部契约**:外部抽奖服务需在开奖后调 `settle`,传齐"开奖人 + 参与者 + 金额 + 幂等键"。本设计只定 SeAT 侧;外部实现另案。
