# 08 · 抽奖服务器对接指南

> 本文面向**外部抽奖服务器**开发者，说明抽奖项目需要如何使用 `seat-pap` 提供的跳转、余额查询与开奖结算 API。
>
> - API 字段级说明见 [`06-API使用说明.md`](06-API使用说明.md)。
> - 当前有效架构设计见 [`05-抽奖外移与PAP银行化设计.md`](05-抽奖外移与PAP银行化设计.md)。
> - 本文重点不是重复接口文档，而是说明**抽奖服务器自己必须承担哪些职责、哪些事情不能交给 SeAT 做**。

---

## 1. 总结：现有 SeAT API 已足够启动抽奖服务器开发

当前 `feat/pap-bank-externalize` 分支已经具备抽奖服务器所需的 SeAT 侧前置能力：

| 能力 | SeAT 入口 / API | 抽奖服务器用途 |
|---|---|---|
| 用户进入抽奖 | `GET /calendar/lottery/redirect` | SeAT 302 跳转外部抽奖地址，并携带 JWT |
| 用户身份认证 | JWT（读 token 签名） | 抽奖服务器验签后建立自己的 session |
| 余额查询 | `GET /api/calendar/paps/{character_id}` / 批量接口 | 展示当前可用 PAP，做购买前校验 |
| 开奖后落账 | `POST /api/calendar/paps/lottery/settle` | 把整场抽奖扣款一次性写回 SeAT |
| 事后纠错 | SeAT `/calendar/audit` 行动审查 | 结算后人工奖励 / 扣除 / 修正 |

因此，可以开始开发抽奖服务器。需要特别注意：**当前模式不是购买节点时实时扣 PAP，而是开奖后一次性 settle。**

---

## 2. 最重要的业务边界

### 2.1 抽奖服务器负责玩法，SeAT 负责 PAP 账本

抽奖服务器负责：

- 用户 session / 登录态；
- 抽奖期数、奖品、节点、购买记录；
- 节点分配、售罄判断、提前开奖规则；
- 随机开奖、中奖记录、开奖审计日志；
- 本地待结算账本与购买期防透支；
- 开奖后调用 SeAT `lottery/settle`。

SeAT 负责：

- 用户从 SeAT 跳转时签发 JWT；
- 提供主角色聚合后的 PAP 余额查询；
- 开奖后把整场扣款写成一个消费型 operation；
- 让该 operation 进入行动审查，供 FC 事后纠错；
- 角色页、军团页、API 统计自动体现最终 `paps.value`。

### 2.2 不要把 `debit/refund` 用在抽奖购买上

`POST /api/calendar/paps/debit` 与 `POST /api/calendar/paps/refund` 当前只是**未来 PAP 商店预留接口**。

抽奖服务器不要在用户买节点时调用 `debit`，也不要在开奖后用 `refund` 纠错。抽奖主链路只有一个写接口：

```http
POST /api/calendar/paps/lottery/settle
```

结算后的 PAP 修正走 SeAT 行动审查，而不是再由抽奖服务器发 refund。

### 2.3 `settle` 允许扣成负数，不替你防透支

`lottery/settle` 的语义是「把外部已经发生的一场抽奖结果落账」。它不会因为余额不足而拒绝，允许把用户 PAP 扣成负数。

这意味着：

- 抽奖服务器如果希望购买阶段不透支，必须自己做购买前余额校验与本地冻结 / 待结算统计；
- 如果允许赊账，可以直接记录购买并在开奖时 settle；
- 如果希望全系统强一致防双花，当前 API 不提供跨系统实时冻结能力，需要后续另行设计 reservation / hold 接口；不要偷用 `debit/refund` 破坏当前抽奖结算模型。

## 3. 推荐整体时序

```text
用户浏览器
  │
  │ 点击 SeAT 侧边栏「超网抽奖」
  ▼
SeAT /calendar/lottery/redirect
  │ 生成 JWT：sub、main_character_id、name、balance、iat、exp
  │ 302 Location: <LOTTERY_URL>?token=...
  ▼
抽奖服务器 /auth/seat?token=...
  │ 验签 JWT + 检查 exp
  │ 用 sub(user_id) 查找 / 创建本地用户
  │ 更新 main_character_id / name / balance_snapshot
  │ 建立抽奖服务器自己的 session
  ▼
抽奖页面
  │ 展示期数、节点、余额
  │ 如需实时余额，调用 SeAT 读 API 查询
  ▼
用户购买节点
  │ 抽奖服务器本地事务：锁用户 / 锁期数 / 校验本地可用额 / 分配节点 / 记录 purchase
  │ 此时不要调用 SeAT 扣款
  ▼
开奖
  │ 抽奖服务器抽中奖节点并固化 draw_log
  │ 汇总本场每个参与者应扣 PAP
  ▼
POST SeAT /api/calendar/paps/lottery/settle
  │ 成功后保存 operation_id / settled_at / settle payload hash
  ▼
SeAT 行动审查
  │ 抽奖 action 可被 FC 查看与纠错
```

## 4. 用户身份：必须以 `sub` / SeAT user_id 为主键

SeAT 跳转 JWT payload 示例：

```json
{
  "sub": 120,
  "main_character_id": 2118151113,
  "name": "Akina",
  "balance": 9.00,
  "iat": 1711699200,
  "exp": 1711699260
}
```

抽奖服务器必须遵守：

1. **本地用户主键使用 `sub`（SeAT user_id）**。
2. `main_character_id` 与 `name` 只做显示字段，每次跳转可更新。
3. 不要用 character_id 当用户主键：用户切换主角色后 character_id 可能变化。
4. JWT 有效期只有 60 秒，只用于完成跳转认证；验签后应建立抽奖服务器自己的 session。
5. 验签必须检查 HMAC-SHA256 签名和 `exp`，不能只 decode payload。

JWT 签名密钥是 SeAT 设置页生成的**读 token**（`kassie.calendar.api_token`），算法：

```text
HMAC-SHA256(base64url(header) + "." + base64url(payload), READ_TOKEN)
```

## 5. 余额与本地待结算账本

### 5.1 SeAT 返回的余额含义

余额查询：

```http
GET /api/calendar/paps/{character_id}?breakdown=1
Authorization: Bearer <READ_TOKEN>
```

重要字段：

| 字段 | 说明 |
|---|---|
| `total_pap` | 对外可消费余额，`available_pap` 小于 0 时兜底为 0 |
| `attendance_pap` | 出勤 PAP |
| `consumed_pap` | 消费 PAP |
| `available_pap` | 当前可用 PAP，可为负 |
| `character_id` | SeAT 归并后的主角色 ID |
| `user_id` | SeAT user_id，应等于 JWT `sub` |

抽奖服务器展示余额一般用 `total_pap`；内部如果要显示欠账，可以用 `available_pap`。

### 5.2 `balance` 快照不能直接当作最终可买额度

JWT 里的 `balance` 只是用户点击跳转那一刻的快照：

- 可能已经过期；
- 不包含抽奖服务器本地尚未 settle 的购买；
- 不保证和用户当前 SeAT 余额完全一致；
- 只适合首屏展示或减少首次 API 调用延迟。

购买前建议重新调用余额 API，或在 session 初始后做一次后台刷新。

### 5.3 推荐本地可购买额度公式

如果抽奖服务器希望尽量避免用户超买，建议维护本地待结算金额：

```text
本地可购买 PAP
  = SeAT 当前 total_pap
  - 本服务内该 user 所有未 settle 的购买金额
  - 本次购买金额
```

判断应放在抽奖服务器数据库事务内完成：

```text
BEGIN
  锁 user 余额行 / purchase 汇总行
  锁 lottery round 行
  重新计算本地 pending_spent
  如 seat_total_pap - pending_spent < 本次购买金额：拒绝购买
  分配节点
  写 purchase / node ownership
COMMIT
```

注意：这个公式只能防止**本抽奖服务内部**重复花费。如果同一个用户同时在其他外部系统消费 PAP，而那些系统也不实时锁 SeAT 余额，则仍可能在最终 settle 后变成负数。当前设计接受这种可能性，靠行动审查与后续业务规则处理。

## 6. 推荐抽奖服务器数据模型

具体表结构由外部项目决定，但建议至少区分以下概念。

### 6.1 用户表

建议字段：

| 字段 | 说明 |
|---|---|
| `seat_user_id` | 主键，对应 JWT `sub` |
| `main_character_id` | 最近一次跳转看到的主角色 ID |
| `name` | 最近一次跳转看到的主角色名 |
| `last_balance_snapshot` | 最近一次 JWT 或 API 得到的余额快照 |
| `last_seen_at` | 最近登录时间 |

### 6.2 抽奖期数表

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 本地期数 ID |
| `title` | 展示标题，同时可作为 SeAT operation 标题来源 |
| `status` | `open` / `sold_out` / `drawn` / `settling` / `settled` / `cancelled` |
| `node_count` | 总节点数 |
| `node_price` | 单节点价格 |
| `max_nodes_per_user` | 每人上限 |
| `allow_repeat_winners` | 是否允许同一用户重复中奖 |
| `draw_log` | 开奖审计 JSON |
| `seat_operation_id` | settle 成功后 SeAT 返回的 operation_id |
| `ref_group` | 发给 SeAT 的场次键，如 `lottery:<id>` |
| `idempotency_key` | 发给 SeAT 的整场幂等键 |
| `settled_at` | SeAT settle 成功时间 |

### 6.3 节点与购买表

建议保留购买明细，而不是只存用户总额：

| 表 / 字段 | 说明 |
|---|---|
| `lottery_nodes.node_number` | 节点号 |
| `lottery_nodes.user_id` | 购买者 SeAT user_id |
| `lottery_nodes.purchased_at` | 购买时间 |
| `lottery_purchases.user_id` | 购买者 |
| `lottery_purchases.amount` | 本笔购买总额 |
| `lottery_purchases.node_numbers` | 本笔买到的节点列表 |
| `lottery_purchases.status` | `pending` / `settled` / `cancelled` |

settle payload 可以从购买明细生成 `participants`。

## 7. 购买节点时的推荐规则

购买接口建议至少校验：

1. 抽奖期数必须是 `open`。
2. 剩余节点数足够。
3. 单用户购买总节点数不超过 `max_nodes_per_user`。
4. 单次金额和用户本场累计金额不超过业务上限。
5. 如不允许透支：`SeAT total_pap - 本地未结算消费 >= 本次金额`。
6. 节点分配必须在事务内完成，避免并发超卖。

推荐做法：

- 用数据库事务锁抽奖期数行；
- 对同一用户购买串行化；
- 随机选择未售节点；
- 写 purchase 明细和 node ownership；
- 提交后再返回前端。

不要在购买事务里调用 SeAT `settle`、`debit` 或 `refund`。

## 8. 开奖与 settle

### 8.1 开奖前先固化本地结果

开奖应先在抽奖服务器本地完成：

1. 锁定抽奖期数；
2. 确认状态允许开奖；
3. 固化有效节点池；
4. 使用可靠随机数抽取中奖节点；
5. 写中奖记录与 `draw_log`；
6. 将状态改为 `drawn` 或 `settling`；
7. 再调用 SeAT `lottery/settle`。

这样即使 SeAT 调用临时失败，也可以用同一 payload 重试，不会改变开奖结果。

### 8.2 settle payload 必须稳定

示例：

```json
{
  "ref_group": "lottery:3",
  "settled_by_character_id": 2118151113,
  "title": "第3期超网抽奖",
  "idempotency_key": "lottery-3-settle",
  "participants": [
    {
      "character_id": 2118151113,
      "amount": 10.00,
      "reason": "押注节点 #03, #07"
    },
    {
      "character_id": 2118151114,
      "amount": 5.00,
      "reason": "押注节点 #11"
    }
  ]
}
```

要求：

- `ref_group`：同一场次永远相同，建议 `lottery:<local_round_id>`；
- `idempotency_key`：同一场次 settle 重试永远相同，建议 `lottery-<local_round_id>-settle`；
- `title`：用于 SeAT operation 标题；
- `settled_by_character_id`：开奖人角色 ID，可为主角色或 alt，但必须绑定 SeAT user；
- `participants`：本场实际参与扣款清单，`amount` 是正数，SeAT 会写成负 PAP；
- `reason`：人读明细，建议包含节点号，长度 ≤255。

同一个用户的多个 alt 如果都参与，SeAT 会归并到主角色。你可以：

- 按购买明细发多条 participant，保留更细审计；或
- 在本地先按用户聚合成一条，reason 写节点列表。

如果希望 SeAT 行动审查能看见每笔购买明细，建议保留多条 participant。

### 8.3 幂等与冲突处理

SeAT 规则：

| 场景 | 结果 |
|---|---|
| 首次 settle | 200，`idempotent_replay=false` |
| 同 `idempotency_key` + 同 payload 重试 | 200，`idempotent_replay=true` |
| 同 `ref_group` + 同 payload 重试 | 200，按幂等回放 |
| 同 `idempotency_key` 或 `ref_group`，但 payload 不一致 | 409 |

抽奖服务器必须保存首次发送的 settle payload 或其 hash。重试时必须使用同一份 payload，不要重新拼接出不同的 `reason`、金额、参与者清单。

### 8.4 成功后保存 SeAT operation

成功响应示例：

```json
{
  "status": "success",
  "operation_id": 123,
  "idempotency_key": "lottery-3-settle",
  "idempotent_replay": false,
  "participants": [
    {"character_id": 2118151113, "balance_after": -5.00},
    {"character_id": 2118151114, "balance_after": 12.50}
  ]
}
```

抽奖服务器应保存：

- `operation_id`；
- `settled_at`；
- `idempotency_key`；
- `ref_group`；
- settle payload / payload hash；
- 每个用户的 `balance_after`（可选，仅供展示 / 审计）。

## 9. 错误处理要求

抽奖服务器必须显式处理以下状态。

| 状态码 | 典型原因 | 推荐处理 |
|---|---|---|
| 200 | 成功 / 幂等重放 | 标记本地期数 `settled`，保存 `operation_id` |
| 401 | 写 token 错或缺 | 停止重试，告警配置错误 |
| 404 | 开奖人角色未找到或未绑定 user | 修正开奖人配置 / 角色绑定后重试 |
| 409 | 同 key / 同场次已存在但 payload 不一致 | 不要自动覆盖；进入人工处理 |
| 422 | 参数错误、参与者未绑定、金额超限 | 修正本地数据后再重试；必要时人工介入 |
| 429 | Laravel API 限流 | 读取 `Retry-After` 后延迟重试 |
| 503 | 写 token 未配置、结算锁忙、账户锁忙 | 延迟重试；多次失败后告警 |
| 5xx / 网络错误 | 临时故障 | 用同一 payload 指数退避重试 |

重点：**只有使用完全相同的 payload 重试才安全。**

## 10. 安全要求

1. SeAT 读 token / 写 token 只能存服务端，不能发给浏览器。
2. JWT 验签必须使用 constant-time 比较，检查 `exp`。
3. 抽奖服务器必须使用 HTTPS。
4. 抽奖服务器 session 时长自行决定，但不能把 SeAT JWT 当长期 session 使用。
5. 购买、开奖、settle 都应有服务端权限校验，不要只靠前端隐藏按钮。
6. settle 的 `reason` 是审计文本，应避免写入隐私信息或不可读机器串。
7. 日志中不要明文打印读 / 写 token。

## 12. 当前不建议做的事

- 不要在抽奖购买时实时调用 `debit`。
- 不要用 `refund` 处理抽奖纠错。
- 不要用 character_id 作为外部用户主键。
- 不要只信 JWT 的 `balance` 快照做长期购买校验。
- 不要在 settle 失败后重新生成不同 payload。
- 不要把 SeAT 的 `total_pap` 当作已经扣除了本抽奖服务未 settle 购买的余额。

## 13. 如果未来要更强的一致性

当前 API 支持的是「外部抽奖服务器先记玩法账，开奖后 SeAT 统一落账」。这对抽奖业务已经足够简单、可审计，也能让纠错回到行动审查。

如果未来业务要求：

- 购买节点瞬间就必须全局扣 PAP；
- 多个外部系统之间不能有任何双花窗口；
- 抽奖购买必须支持逐笔取消 / 退款并立即体现在 SeAT；

则需要另行设计 PAP reservation / hold / capture / release 语义，或者重新评估是否启用商店式 `debit/refund`。这不属于当前抽奖外移方案的前置条件。当前开发抽奖服务器时，应按本文的 settle 模型实现。
