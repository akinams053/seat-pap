# 第一部分 · PAP 超网抽奖设计（阶段 1–6，已完成）

目标：在插件内实现类 EVE HyperNet Relay 的 PAP 抽奖。FC 创建「抽奖行动」，成员用 PAP 购买节点，开奖后按节点抽取中奖者；PAP 扣除通过现有行动审查链路落库，便于审计和事后调整。

推荐定义：

> **PAP 超网抽奖是一种特殊 operation。成员购买节点时系统在该 operation 下生成负数 PAP 调整；行动审查负责 PAP 扣除审计和事后金额调整，抽奖模块负责节点、奖品、开奖和退款。**

## 1. 产品决策

- **扣除模型**：抽奖行动扣除。每期抽奖绑定一个特殊 `Operation`，购买写负数 `PapAdjustment`，`Pap::recomputeValueFor()` 回写 `paps.value`。不做独立 PAP Wallet。
- **创建入口**：专用 PAP 抽奖页面，系统自动创建并绑定特殊 operation；不改造现有 operation 创建表单。
- **权限**：查看 = `calendar.view`；创建 = `calendar.create`；管理自己的抽奖 = 创建者 / operation FC；管理全部 + 开奖 / 取消 = `calendar.setup`。开奖 / 取消必须手动点击。
- **节点购买**：随机分配节点 + 成员选购买数量。FC 创建时设单节点价格、总节点数、每人上限（仅基本校验：正数、不超 `decimal(8,2)`、上限 ≤ 总数）。
- **开奖规则**：多奖顺序抽，每奖抽一个中奖节点；「是否允许同一用户重复中奖」每期可配。
- **退款**：只有 FC / 管理员手动取消时才全额退款（写正数 `PapAdjustment`），不删历史购买记录。
- **可见范围**：公开节点归属（已售节点显示购买者主角色，自己的节点高亮，开奖后中奖节点高亮）。
- **审查与节点解耦**：行动审查手动奖惩只调 PAP 金额，**不影响节点数量或中奖概率**。

### 提前开奖（2026-05 决策变更）

应运营「凑不满人」需要新增：`open` 状态下，已有 ≥1 个已售节点时，FC / 管理员可手动「提前开奖」。

- 候选池只从已售节点抽；未售节点开奖时作废（`voided_at`）；`draw_log.draw_mode = early`。
- 售满后正常开奖记 `sold_out`。
- 一个节点都没卖出时不显示开奖按钮，只能继续购买或取消退款。
- 此变更覆盖早期「必须售完才能开奖」的旧约束。

## 2. 核心业务流程

1. **创建**：FC 填标题 / 奖品 / 总节点数 / 单价 / 每人上限 / 是否允许重复中奖 → 系统建特殊 operation（标题前缀 `【抽奖】`）+ 绑定保留 tag + 建 lottery / prize / node 记录 → 进入 `open`（第一版不做 `draft`）。
2. **购买**：校验 `open` / 剩余 / 每人上限 / 可用 PAP → 事务内随机分配未售节点 → 确保该成员在抽奖 operation 下有 PAP 行 → 写负数 `PapAdjustment`（`value = -(数量 × 单价)`，reason 记节点号）→ `recomputeValueFor()` 回写。
3. **开奖**（售满 / 提前）：锁 lottery 主行、再确认状态 → 按奖品顺序从有效节点池随机抽 → 保存中奖奖品 / 节点 / 用户 / 主角色 + `draw_log` + 开奖人 / 时间 → 状态 `drawn`。不允许重复中奖时，用户中奖后其剩余节点排除出后续抽取。
4. **取消退款**：锁主行，仅 `open`/`sold_out` 且未开奖可取消 → 按已购节点写正数退款调整 → `recomputeValueFor()` → 状态 `cancelled`。

## 3. 抽奖专用 Tag（关键约束）

```
name = PAP 抽奖 / Lottery
quantifier = 0
analytics = lottery
```

- 创建抽奖时系统自动创建 / 查找并绑定；FC 不手动选普通 PAP tag。
- 系统保留 tag，普通 tag 管理中禁止删除、禁止改 quantifier。
- **统计主识别**：以 `kassie_calendar_lotteries.operation_id` 判断是否抽奖 operation；抽奖 tag 仅作 UI / 筛选辅助。
- **抽奖基础 PAP 必须为 0**：`recomputeValueFor()` = `operation tag max(quantifier) + Σadjustments`，tag quantifier 非 0 会导致扣费金额错误。

## 4. 数据设计

### `kassie_calendar_lotteries`（抽奖主表）
`id` / `operation_id`(unique) / `title` / `node_count` / `node_price`(decimal(8,2)) / `max_nodes_per_user` / `allow_repeat_winners` / `status`(open/sold_out/drawn/cancelled) / `created_by_character_id` / `drawn_by_character_id` / `drawn_at` / `draw_log`(json) / timestamps。索引：`operation_id` unique、`status`、`created_by_character_id`。

### `kassie_calendar_lottery_prizes`（多奖品表）
`id` / `lottery_id` / `sort_order` / `name` / `description` / `winner_node_number` / `winner_user_id` / `winner_character_id` / `drawn_at`。索引：`(lottery_id, sort_order)`、`(lottery_id, winner_user_id)`。

### `kassie_calendar_lottery_nodes`（节点表，创建时预生成全部节点）
`id` / `lottery_id` / `node_number` / `user_id` / `character_id` / `pap_adjustment_id` / `purchased_at` / `refunded_at` / `voided_at`。约束：`unique(lottery_id, node_number)`、`index(lottery_id, user_id)`、`index(pap_adjustment_id)`。

### 前置 schema 改造（阶段 1 最先做，已完成）
- `kassie_calendar_paps.value`：`decimal(5,2)` → `decimal(8,2)`（有符号）
- `kassie_calendar_pap_adjustments.value`：`decimal(6,2)` → `decimal(8,2)`（有符号）
- `calendar_tags.analytics` enum 新增 `lottery`

> 原 `paps.value` 仅 `decimal(5,2)`（±999.99），抽奖累计消费会溢出，故必须先拓宽。三处精度（含 `node_price`）统一为 `decimal(8,2)`。前向安全，只扩大范围。

## 5. 与现有 PAP / 审查的集成

- 购买时若无 PAP 行则建：`operation_id = lottery.operation_id`、`character_id = main_character_id`、`join_time = now`、`ship_type_id = 0`、`value = 0`（再 recompute）。**不**通过 ESI fleet 创建（抽奖非真实舰队）。
- 扣费 / 退款都追加 `PapAdjustment`，不删原记录，审计链完整。
- **审查列表层面**：抽奖行动因有 PAP 记录自动出现在审查列表，作为 1 行（= 1 operation）。给它加「抽奖」徽标（靠 `analytics = lottery` 或 join `lotteries`）；单 PAP 显示 `—`（非 0）；总额负数显示「消费 PAP xxx」；明细弹窗提供跳转抽奖详情链接。
- **成员明细弹窗**几乎零改动：每个成员的 `value` 是净消费（负数），`adjustments` 天然展示每条购买扣费 / 退款。`paps` 以 `(operation_id, character_id)` 为主键，一个人在一个抽奖里只有一条 pap 记录，买多次只累加 adjustment。

## 6. 并发、一致性、状态机

- **购买放事务内**：锁 lottery 主行 → 确认 `open` → 锁未售节点 → 锁内重新校验剩余 / 上限 / 余额 → 随机选节点 → 更新归属 → 建 / 确保 PAP 行 → 写负数 adjustment → recompute → 提交。不能超卖、同节点只能买一次、余额不足不能买、任一步失败整体回滚。第一版采用**锁 lottery 主行串行购买**（牺牲峰值并发换正确性）。
- **幂等**：建议购买支持 `request_id`（`lottery_id + user_id + request_id` 唯一）；开奖 / 取消 / 退款靠状态机 + 事务 + 唯一约束防重复。
- **余额延迟**：页面「可用 PAP」仅提示，购买提交时事务内重算，不足返回明确错误。
- **开奖不在购买请求内执行**：最后一个节点购买只标 `sold_out`，开奖单独加锁。
- **状态机**：`open → sold_out → drawn` / `open →(提前开奖) drawn` / `→ cancelled`。`draft` 仅保留为未来扩展。
- **前端**：无 WebSocket；抽奖详情页 5 秒短轮询轻量 JSON（`lottery.snapshot`），`open`/`sold_out` 时检测变化整页刷新，后台标签页跳过本轮。

## 7. 开奖审计 `draw_log`

```json
{
  "draw_mode": "sold_out",
  "allow_repeat_winners": false,
  "rounds": [
    { "prize_id": 1, "prize_name": "一等奖", "candidate_node_count": 128,
      "roll_index": 37, "winner_node_number": 42, "winner_user_id": 15, "winner_character_id": 2118151113 }
  ]
}
```

售满 `draw_mode = sold_out`；提前开奖 `early`（未售节点作废，不参与抽取）。随机数用 PHP `random_int()`。

## 8. 抽奖关键风险（务必遵守）

- **抽奖基础 PAP 必须为 0**：保证抽奖 tag `quantifier = 0`（见 §3）。
- **购买后不要再 plain-save `Pap`**：`Pap::save()` 每次把 `value` 重置为 `tags.max(quantifier)`（抽奖即 0）。首次建行用 `save()`（value=0 正确），之后扣费 / 退款**只走 `recomputeValueFor()`**。
- **抽奖可用 PAP 用独立查询，不要 floor 到 0**：不能复用商店 API 的 `max(0, …)`，否则透支用户「看起来有 0、实则欠账」。购买校验事务内重算。
- **严格防重复退款 / 重复开奖**：`drawn` 后不能取消 / 退款，`cancelled` 后不能再退款。

# 第二部分 · 阶段 7 PAP 统计口径设计（设计 + 决策，代码未落地）

> 落地步骤、只读巡检、宿主验证 SQL 见 [`03-近期计划.md`](03-近期计划.md)。本部分只定义口径语义与已拍板决策。

## 9. 背景与目标

抽奖引入消费型 PAP 后，`kassie_calendar_paps.value` 已不只是「出勤获得」，而是：

```
paps.value = 基础 PAP + 全部审查 / 抽奖 adjustments 后的最终净值
```

这对审查 / 抽奖 / 商店余额正确，但统计页面会语义混乱（正向=出勤、负向=消费、0 可能是从未获得 / 退款 / 清零）。阶段 7 在**最小修改原则**下统一口径为：

```
出勤 PAP / 消费 PAP / 当前可用 PAP
```

不改 `paps.value` 存储语义、不改 `recomputeValueFor()`。

## 10. 数据语义（不变）

- **`kassie_calendar_paps.value`**：单个 operation + character 的最终净值（基础 PAP 由 tag max quantifier 设定，审查 / 抽奖 / 退款 / 清零写 adjustment 后 recompute 回写）。
- **`kassie_calendar_pap_adjustments.value`**：调整流水 / ledger delta（手动奖 +、手动罚 −、抽奖购买 −、退款 +、清零反向冲正）。基础 PAP 不在 adjustment 表中。

## 11. 三个业务口径（已决策：带符号定义，恒等式精确成立）

通过 `LEFT JOIN kassie_calendar_lotteries l ON l.operation_id = p.operation_id` 区分抽奖 operation（`operation_id` 唯一，1:1，不放大行数）。

### 11.1 出勤 PAP — 普通行动全部最终值（带符号）

```sql
SUM(CASE WHEN l.id IS NULL THEN p.value ELSE 0 END) AS attendance_pap
```

- 含基础 PAP、审查奖励、扣罚后最终值、清零后为 0；
- **普通行动被扣成负数时，该负值作为惩罚计入出勤 PAP**（不丢弃、不另设第四类，见 §13）；
- 可能为负，惩罚会压低贡献，这是预期行为；
- 军团成员贡献排行默认按它排序。

### 11.2 消费 PAP — 抽奖行动全部最终值取负（带符号）

```sql
SUM(CASE WHEN l.id IS NOT NULL THEN -p.value ELSE 0 END) AS consumed_pap
```

- 正常抽奖最终值为负 → 取负后为正消费；
- 当前净消费，非历史累计；退款后抽奖 `paps.value = 0`，不再计入；
- **抽奖出现正数 = 异常**，不在公式特判（见 §13），通过巡检 + 告警暴露。

### 11.3 当前可用 PAP — 所有最终值求和

```sql
SUM(p.value) AS available_pap
```

- 用途：抽奖 / 商店余额判断、兼容 API `total_pap`、个人页「还剩多少可用」；
- 内部页面可显示负数；对外 API 继续 `max(0, available_pap)` 兜底。

### 11.4 恒等式（已决策）

普通 + 抽奖恰好覆盖全部行且互不重叠，因此：

```
attendance_pap - consumed_pap
  = SUM(l.id IS NULL 的 value) - SUM(l.id IS NOT NULL 的 -value)
  = SUM(全部 value) = available_pap   ← 任何边界都精确成立
```

页面同时展示三个数不会「加不起来」。**这正是改用带符号定义、而非按正负号拆分的原因**：正数不一定永远是出勤、负数不一定永远是消费，按来源类型（是否抽奖）拆分才能自洽。

## 12. 全局 PAP 起始日（已决策）

为根除「个人页 / 军团页按 year/month 无下限、API 硬编码 `2026-01-01`」的日期口径割裂：

```
起始日之前的数据保留但不再参与统计与消费；起始日及之后正常统计、排行、消费。
```

决策与实现约束：

1. **单一来源**：唯一权威配置，所有查询只读它。建议封装访问器（如 `Pap::statisticsStartDate()`）。
2. **存储与 UI**：复用现有全局设置机制，新增 `setting('kassie.calendar.pap_start_date', true)`，在**现有设置页**（`SettingController`）加字段。
3. **粒度**：**强制月初对齐**（避免个人页按月分组出现「半个月」）。
4. **过滤列**：统一用 `kassie_calendar_paps.join_time`（`Pap::save()` 中 week/month/year 均由 join_time 派生，抽奖购买 join_time = 购买时间，与 year/month 分组一致）。
5. **覆盖四处**（全部统一读起始日）：

   | 入口 | 现状 | 调整 |
   |---|---|---|
   | 个人页 `CharacterController` | 无日期下限 | 加 `join_time >= 起始日` |
   | 军团页 `CorporationController` | 无日期下限 | 加同样过滤 |
   | API `ApiController` | 硬编码 `2026-01-01` | 默认改读起始日 |
   | 抽奖余额 `LotteryController` | 锁死 `2026-01-01` | 改读同一起始日 |

6. **API `since` 关系**：仍接受 `since`，但 clamp 为 `max(since, 起始日)`，外部永远查不到起始日之前。
7. **前移风险**：起始日往后挪可能截断已发生抽奖消费对应的出勤来源，使可用 PAP 凭空变负。本次是全新设计定**初始**起始日、抽奖也是新功能，不会撞上；设置页加说明，提示别把起始日调到已有抽奖消费之后。

## 13. 数据边界处理（已决策）

- **§13.1 普通行动被扣成负数**：作为惩罚计入出勤 PAP（见 §11.1），不改 `recomputeValueFor()`，是否允许扣到负数仍由 FC 审查把握，统计层如实反映。
- **§13.2 抽奖行动出现正数 = 异常**（手动补偿 / 异常退款 / 测试残留）：**不**在消费公式特判（保持恒等式），增加只读巡检：

  ```sql
  SELECT * FROM kassie_calendar_paps p
  JOIN kassie_calendar_lotteries l ON l.operation_id = p.operation_id
  WHERE p.value > 0;
  ```

  命中则在**抽奖管理页 / 行动审查页**显示**告警徽标**，提示人工核查修正。

## 14. 主角色聚合规则（阶段 7 必须继续遵守）

```
用户维度统计优先按 SeAT user.main_character_id 聚合该用户所有 alt。
```

1. 个人页：用当前角色所属用户的 `associatedCharacterIds()`；
2. 全局排行榜：`refresh_tokens → users → main_character_id`，无用户时 fallback 原角色 ID；
3. 军团页：先按 `character_affiliations.corporation_id` 过滤军团内角色，再聚合到 main character；
4. API：按目标角色所属 SeAT user 全部关联角色聚合；
5. **main character join 不要改成 inner join**，避免未绑定 / 异常角色丢失。

## 15. 各入口现状与调整方向（设计）

- **个人页**（`CharacterController` + `character/paps.blade.php` + `ranking_table.blade.php`）：当前全 `SUM(value)`。调整：当月 / 当年增加 attendance / consumed / available breakdown，Blade 信息块明确三个数，趋势图标题 / tooltip 说明口径。排名表进度条除零已修复。
- **军团页**（`CorporationController` + `corporation/paps.blade.php`）：`getGroupedRanking()` 增加三字段（旧 `qty` 暂留为 available 兼容前端），排行默认按出勤 PAP DESC；表格 / CSV 增加列（CSV 格式变化需提示）；趋势图返回三列；`getTypeDistribution()` 暂不大改（先改标题，避免 tag 多对多 join 放大）。
- **API**：见 §12 第 6 点（`since` clamp）+ [`01-项目说明.md`](01-项目说明.md) §6.4（保持 `total_pap` 兼容，可选 breakdown）。
- **审查页**：已接近 ledger 语义，暂非第一优先级；保留抽奖特殊显示；后续文案区分普通=出勤、抽奖=消费；不破坏清零与流水。
- **抽奖余额**（`LotteryController`）：继续用当前可用 PAP（不能改成出勤 PAP，否则可重复花已消费的 PAP），起点改读全局起始日。

## 17. MySQL 聚合别名 gotcha（实现时务必注意）

MySQL **不允许**在 `ORDER BY` / `HAVING` 中通过别名引用聚合函数结果（报 `Reference '...' not supported (reference to group function)`）：

```php
->selectRaw('MAX(p.created_at) as latest_pap_at')
->orderByRaw('latest_pap_at DESC')      // ❌
->orderByRaw('MAX(p.created_at) DESC')  // ✅
```

普通列别名可以；聚合别名必须在 `ORDER BY` / `HAVING` 写完整表达式。
