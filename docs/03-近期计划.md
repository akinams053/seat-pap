## 2. 阶段 B — 审查列表过滤改 OR(抽奖回审查页)

**目标:** 行动审查列表从"只显示出勤"改成"显示出勤 + 抽奖,排除商店锚"。

**文件:** `AuditController::operationsJson()`(:44–70)。

**现状:** 两处 `->where('o.is_consumption', 0)`(line 63、68)把所有消费排除。

**改法:** 关联 `calendar_tags` 判断 lottery,过滤条件改为 **`is_consumption = 0 OR analytics = 'lottery'`**:
```php
// 大意(实现时按现有 query builder 结构落):
->leftJoin('calendar_tag_operation as cto', 'cto.operation_id', '=', 'o.id')
->leftJoin('calendar_tags as t', 't.id', '=', 'cto.tag_id')
->where(function ($q) {
    $q->where('o.is_consumption', 0)
      ->orWhere('t.analytics', 'lottery');
})
->groupBy('o.id')   // join 后去重
```
⚠️ 两处过滤(:63 列表、:68 计数 recordsTotal)都要同步改,否则分页计数对不上。
⚠️ join 后注意聚合别名 gotcha(见 CLAUDE.md):`ORDER BY` / `HAVING` 用完整表达式,别用别名。

**前端:** 抽奖行重新出现后,可能要恢复「抽奖」徽标 / 「单 PAP 显示 —」/「总额负数显示消费 PAP」(bank 退役时清掉过 `is_lottery` 分支,查 `views/audit/` 前端 + `membersJson` 已能给 `analytics`,:135)。

**验证:** 抽奖 operation 出现在审查列表、商店锚不出现;`membersJson` 对抽奖行返回正确;恒等式 `出勤 − 消费 = SUM(value)` 不变。

## 3. 阶段 C — 「开奖结算」settle 接口(核心)

### 3.1 路由
`src/Http/routes.php` 写接口组(line 25–41,`middleware: calendar.api.write_token`)加:
```php
Route::post('/paps/lottery/settle', [
    'as' => 'api.calendar.paps.lottery.settle',
    'uses' => 'ApiController@lotterySettle',
]);
```

### 3.2 控制器 `ApiController::lotterySettle()`
契约见 07 §4.1。逻辑(单事务 + GET_LOCK,参考现有 `handleLedgerWrite` + `standingFor`):

1. **validate**:`ref_group`(必)、`settled_by_character_id`(必,int)、`title`(必)、`idempotency_key`(必,≤128)、`participants`(必,array;每项 `character_id`/`amount`/`reason`)。
2. **幂等**:用 `idempotency_key` 查是否已建过该场 operation → 命中直接返回旧 `operation_id`。
   - **落点(实现时定)**:复用 `calendar_operations.consumption_key` 唯一列承载 `idempotency_key`(standingFor 已降商店预留、抽奖不再用该列建月度锚,空闲可复用,**不必加新 migration**);或新增 `settle_key` 列。
3. **解析负责人**:`settled_by_character_id` → `RefreshToken::find` → user → 主角色;作 operation 的 `user_id`(user->id) / `fc_character_id`(主角色,**满足外键,勿填 0**,见 [[bank-debit-userid-fk-bug]] 教训)。
4. **建 operation**:`title`、`is_consumption = 1`、`importance = 0`、`start_at/end_at = now`、`consumption_key = idempotency_key`(幂等用);保存后 `$op->tags()->attach(Lottery::reservedTag()->id)` 挂 lottery tag(`reservedTag` 在 `Models/Lottery.php:75`)。
5. **按 user_id 串行化**:对每个参与者用其 user 的 `GET_LOCK`,或整场一把锁(防并发重复结算)。
6. **逐参与者**:`character_id` → 主角色聚合 → `Pap::firstOrCreate(op_id, mainChar, ship_type_id=0, join_time=now)` → `PapAdjustment::create(value = -amount, source='lottery', ref_group, reason, created_by=负责人或主角色)` → `Pap::recomputeValueFor(op_id, mainChar)`。
   - **余额不足照扣成负**(决策 5),不阻断;`total_pap` 对外仍 `max(0,…)` 兜底。
7. **返回**:`{ status, operation_id, participants:[{character_id, balance_after}] }`。

### 3.3 要点 / 待实现时确认
- 整场在**一个事务**里写多个参与者,任一失败回滚整场。
- 幂等键唯一约束撞了 = 已结算 → 返回旧结果(不重复建)。
- `reason` 沿用外部传入(节点号等);`ref_group` 即场次键。
- 抽奖 operation `is_consumption=1` + lottery tag → 自动算消费(口径不变)+ 进审查页(阶段 B 的 OR 过滤)。
