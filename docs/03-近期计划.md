### 2.3 API 限流说明

插件 API 已改用自有限流器 `calendar-api`（按调用方 IP **300/min**），替代原先继承宿主 `api` 组的默认 60/min，仅作用于本插件 `api/calendar/*` 路由，不改动宿主全局限流。

结论：

- 正常 `settle` 是一场抽奖一次调用，远低于 300/min。
- 外部服务仍应实现（防御性，不指望触发）：
  - 遇到 `429` 读取 `Retry-After` 后延迟重试。
  - 不要无间隔循环重试。
  - 余额查询优先批量接口，避免高频轮询。
- 如需进一步放宽，改 `CalendarServiceProvider::registerApiRateLimiter()` 里的 `perMinute(300)` 即可。

> 测试服已确认：`php artisan` 应以 `www-data` 执行，直接用 `ubuntu` 会因为 `.env` / log 权限失败。

### 3.2 路由检查

```bash
sudo -u www-data php artisan route:list | egrep 'lottery/settle|paps/debit|paps/refund|calendar/audit|audit/consumption'
```

期望：

- 有 `api/calendar/paps/lottery/settle`
- 有 `api/calendar/paps/debit`
- 有 `api/calendar/paps/refund`
- 有 `calendar/audit`
- 没有 `calendar/audit/consumption`

### 3.3 数据巡检 SQL

```sql
-- 抽奖行动是否按预期挂 lottery tag 且是消费 operation
SELECT o.id, o.title, o.is_consumption, t.analytics, p.value
FROM calendar_operations o
JOIN calendar_tag_operation cto ON cto.operation_id = o.id
JOIN calendar_tags t ON t.id = cto.tag_id
JOIN kassie_calendar_paps p ON p.operation_id = o.id
WHERE t.analytics = 'lottery'
ORDER BY o.id DESC;

-- 商店消费锚不应挂 lottery tag，因此不会进行动审查
SELECT o.id, o.title, o.is_consumption
FROM calendar_operations o
LEFT JOIN calendar_tag_operation cto ON cto.operation_id = o.id
LEFT JOIN calendar_tags t ON t.id = cto.tag_id AND t.analytics = 'lottery'
WHERE o.is_consumption = 1 AND t.id IS NULL;
```

### 3.4 API 探测

- 无 token 调 `settle` 应返回 401。
- 有效 token + 有效角色调 `settle` 应返回 200。
- 同 payload 重放应 `idempotent_replay=true`。
- 同 `ref_group` 改 payload 应返回 409。
- `GET /api/calendar/paps/{alt}?breakdown=1` 应归并到 main character。
