## 4. 接手人必须知道的当前行为

- **开奖按钮何时出现**：售满（`sold_out`）显示「开奖」；`open` 且 ≥1 个已售节点时对 FC / 管理员显示「提前开奖」；一个都没卖出时不显示。
- **提前开奖语义**：`status=open` 且 `sold_count>0` 触发，只从已售节点抽，未售节点写 `voided_at` 作废，`draw_mode=early`。
- **整行动清零语义**：对当前 action 下每个 `paps.value != 0` 成员追加反向 `PapAdjustment` 冲正为 0，不删历史；已是 0 的跳过；未终态 lottery action（`open`/`sold_out`）会被后端拒绝。
- **抽奖消费即时进统计**：负数 `paps.value` 会即时进入角色 / 军团 PAP 统计，使统计混合出勤 / 消费 / 可用——这是阶段 7 要处理的已知现象，非缺陷。

### 6.1 分支间升级 / 降级兼容性

三个分支的迁移是**严格叠加**的（高版本 = 低版本全部迁移 + 新增几个，无人改动他人迁移）：

```
localization
   └─+6→ docs/pap-hypernet-lottery-plan（+audit 表 / widen 精度 / lottery 三表 / …）
            └─+1→ feat/pap-bank-externalize（+ add_bank_ledger_columns）
```

**✅ 升级（低 → 高）始终安全**：`composer update` 切到高版本后跑 `php artisan migrate`，自动补建表 / 加列；`feat` 的回填迁移会把历史抽奖 operation 标 `is_consumption=1`、其调整标 `source=lottery`，旧抽奖数据在新口径下仍算对。

- `localization → lottery-plan`：补建 lottery / audit 表、加列。
- `lottery-plan → feat`：加 `source`/`is_consumption`/`consumption_key` + 回填历史抽奖。
- `localization → feat`：一次跑齐全部 7 个新迁移。

**⚠️ 降级（高 → 低）：原始数据不丢，但统计口径会错**。Laravel `migrate` **只前进、不自动回滚** —— 切回旧分支后多出的表 / 列残留（旧代码不读、且都有默认值 / 可空，**插入也不报错**），`paps.value` 已是「基础 + 调整」净值仍可读，**数据本身不损坏**。但旧代码用旧的消费判定，会看错新机制产生的数据：

- 最典型 `feat → lottery-plan`：feat 期间的外部消费记在 **standing operation**（无 `lotteries` 记录），而 lottery-plan 用 `leftJoin lotteries` 判定消费 → 这些消费 `l.id IS NULL` 被**误算成出勤 PAP**，出勤虚高、口径错乱。
- `feat / lottery-plan → localization`：lottery / audit 数据残留，基础版口径与之不同。

**结论与建议**：

- 把三分支当成**单向升级链** `localization → lottery-plan → feat`，生产上**只升不降**。
- 真要降级：先 `mysqldump` 备份整库，降级后**手动** `php artisan migrate:rollback` 或清理新机制数据，**不能只靠 `composer update`**（它不会回滚 schema）。
- 不要在同一台 SeAT 上反复横跳分支。
- 测试服可先按 `localization → feat` 跑一遍升级，确认数据与统计都对，作为未来生产升级的标准路径。
